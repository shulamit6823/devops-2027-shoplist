# חלק ב- תרחישים

**שאלה 1 – scale**

1. ה־API Server מקבל את הבקשה, בודק שהיא תקינה ושיש הרשאות.
2. ה־etcd שומר את המצב הרצוי החדש: 4 Pods במקום 2.

**שאלה 2 – שלוש בלילה**

אם ה־Container של backend קורס, ה־kubelet מזהה את הקריסה ודואג להפעיל את ה־Container מחדש בעזרת ה־Container Runtime, בתוך אותו Pod.

אם מישהי מוחקת את ה־Pod כולו, ובהנחה שהוא מנוהל על ידי Deployment, ה־Controller Manager, באמצעות הבקרים המתאימים, דואג שייווצר Pod חדש במקומו כדי לשמור על מספר ה־Pods הרצוי.

**שאלה 3 – node נכבה**

אם Node 2 נכבה בענן, ה־Pods שרצו עליו מפסיקים לפעול. Kubernetes מזהה שה־Node אינו זמין, ואם ה־Pods מנוהלים על ידי Deployment, הוא דואג שייווצרו Pods חלופיים על Nodes אחרים שיש בהם מקום.

אם המחשב בכיתה נכבה, גם ה־Cluster של Docker Desktop מפסיק לפעול, כי הוא רץ על המחשב המקומי ואין Nodes אחרים שיכולים להמשיך לעבוד.

### שאלה 4 – מהכיתה לענן

`imagePullPolicy: Never` לא יעבוד כמו בכיתה, כי הוא אומר ל־Kubernetes לחפש את ה־Docker Image רק על ה־Node עצמו ולא להוריד אותו מבחוץ. בכיתה ה־Image היה אצלנו מקומית, אבל ב־EKS ה־Nodes נמצאים בענן ואין להם את ה־Image הזה.

לכן צריך להעלות את ה־Docker Image ל־Registry בענן, למשל Docker Hub או ECR, לעדכן את הכתובת שלו בקובץ ה־YAML ולשנות את `imagePullPolicy` ל־`IfNotPresent` או `Always`.

לגבי `NodePort`, הוא יכול לעבוד גם בענן, אבל המשתמש יצטרך לדעת את הכתובת של אחד ה־Nodes ואת מספר הפורט, וצריך שתהיה אליו גישה ברשת.

לכן עדיף לשנות את סוג ה־Service ל־`LoadBalancer`, כדי שתהיה כתובת כניסה אחת לאפליקציה בלי שהמשתמש יצטרך לדעת לאיזה Node לפנות.
